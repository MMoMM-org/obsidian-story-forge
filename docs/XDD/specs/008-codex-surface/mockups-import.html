Story Forge — Import a collection · import modal L11a–L11i · sibling of L10 · draft for sign-off

Why this page exists. + Import from vault… opens src/import/ImportPickerModal.ts. It is hard to read and use: one column of rows that stack name, description, badge and path; an auto-selected first row; Next → in the footer; refusals only after Next →; and a modal that closes on success without saying anything. L10 (mockups-catalog.html, signed off with Q1–Q8 as recommended) is the catalog sibling. This page redraws the import modal in the same shell, so the two read as one family. What an import does stays as ViewImporter and ImportFlow do it, except where an R# says otherwise.

How to read this file. Light theme is the default. The Dark / Light toggle switches every figure, and L11i is always dark. Tokens, the modal shell and the ct- row, pill and detail patterns are copied from mockups-catalog.html. Tags: L10 Q# = inherited from the signed-off L10 decision, not asked again; P2 / today / ImportFlow = shipped behaviour or text, drawn as it is; R# = proposed here, not decided until you sign it off. Seed files are invented vault paths in the test vault's folder layout.
Inherited from L10 without asking again: two panes, stacked below about 560px (Q1); search plus engine filter only above 5 entries (Q2); nothing selected on open (Q3); one action and its feedback in the detail pane (Q4); the query wrapped and contained (Q5); engine labels Bases, Dataview, DataviewJS (Q7); the neutral note for a closed review (Q8). L10's Q6 (checksum and provenance) has no counterpart: the import modal shows no checksum, and everything here becomes imported.

Proposals — your answer needed (recommended default in each)

  1. R1 — The action and the consent step. (a) One button in the detail pane: Import for Bases and Dataview, which saves at once; Review and import… for DataviewJS, which opens today's full disclosure first. The light DQL confirmation dialog is no longer shown for imports. (b) Same buttons, but Dataview keeps the light dialog as Review and import…. (c) Keep today's Next → in the footer, then a separate consent step for both Dataview engines. Recommended: (a). It matches L10 word for word ("Install" ↔ "Import"). The pane already shows the DQL query and "Safe: declarative query, no code.", so the light dialog repeated it. PRD F7 AC 8 already says "Bases and DQL are enable/disable only". DataviewJS keeps its full gate unchanged. This drops a consent dialog that ships today (ImportFlow.importTokens would compute DQL tokens the way it does for a .base), so it needs a decision-log entry.
  2. R2 — Files that can't be imported. (a) List them with a Can't import status, and show the reason and a fix as soon as the file is selected; (b) hide them; (c) today: a plain row, and the reason only after Next →. Recommended: (a). The scan already parses every candidate when the modal opens (_loadFiles), so the reason is known before you click. Hiding them leaves you wondering why your note is missing. Read and write failures that only happen at import time still appear under the button (L11f(f), (g)).
  3. R3 — What a row's second line shows. (a) engine pill and vault path; (b) engine pill and description, as in L10. Recommended: (a), sorted by path. These are your own files: the path is how you know them, it tells two notes with the same name apart, and a .base has no description at all. The description moves to the detail pane. No folder headers.
  4. R4 — After a successful import. (a) The modal stays open: the row and header turn ✓ Imported, the button goes, and a success line names where it shows. (b) Today: the modal closes and nothing confirms. (c) Close with a Notice. Recommended: (a), as in L10e. You can import several files in one visit, and the result is stated where you acted. Reopening the modal drops imported files, as today.
  5. R5 — "Where it goes". (a) A read-only Shows in line with the P2 default (Bases: Anvil on, Workbench off; Dataview and DataviewJS: Workbench on, Anvil off) and "Change this per collection in Library › Collections."; (b) the two switches in the import pane, so you choose before importing. Recommended: (a). The switches have one home, the Library row (L2). A second copy here would be a second place to set the same fact, and the default is right for most files.
  6. R6 — Refusal wording. Today's messages state the rule but not the fix, and two arrive as a Notice after the picker has closed. Recommended: keep each of today's sentences word for word and add one fix line under it (L11f, table below). Two messages change: the duplicate becomes inline Not imported: <path> is already in Library › Collections. instead of the Notice "Collection already imported", and a closed DataviewJS review shows the neutral Not imported. You closed the review, so nothing was saved. Success says Imported <name>. It is in Library › Collections and shows in the <Anvil | Workbench>.

Placement and announcing. Parse refusals belong to the file, so they sit in its detail pane as soon as it is selected, with role="note": they are read with the pane, not interrupting. Import-time refusals appear under the button with role="alert"; the success and neutral lines use role="status". What this commits us to

When signed off, the import modal is restyled to this: a rendering change in ImportPickerModal on the same CSS as L10's browser (sf-catalog-split, rows, pills, detail, feedback), so the two modals share one set of rules on Obsidian variables. Behaviour changes only where proposed: the DQL light dialog leaves the import path (R1), the modal stays open after an import (R4), and the duplicate and closed-review messages move inline (R6). ViewImporter.parse, scanVault and the DataviewJS disclosure stay as they are. Not in scope: editing the file from here, choosing surfaces here (R5), folder headers, or importing several files with one click.
