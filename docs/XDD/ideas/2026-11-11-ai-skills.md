# AI skills shipped with Story Forge

Brainstormed 2026-11-11 with the user. Builds on `docs/claude-skills.md` (the division "the plugin
renders and edits frontmatter; Claude reasons over it"), which names the analysis skills but not who
ships them. Answer: **Story Forge ships them**, installs them into the vault, and keeps them generic.
Vault-specific behaviour comes from the vault owner's own layer (for the author's vaults: `_forge`),
through a defined extension point — never by editing Story Forge's skills.

Status: idea, not specified. Target: its own spec after the current undo-journal work.

## Problem

- The analysis Story Forge deliberately leaves out of its code (continuity, plot holes, canon
  consistency) only exists if someone writes and distributes the skills. Today a skill like
  `continuity-check` lives in a private infrastructure repo and is copied by hand.
- Users of the public plugin get the views but none of the reasoning.
- Skills written outside the plugin drift from the plugin's schema: field names, relation fields and
  categories change in Story Forge, the skill still describes the old ones.

## Model

```
Story Forge (plugin)                         AI tool (Claude Code / Desktop / Codex / Gemini CLI)
  bundles skills ──"Install AI skills"──▶  <vault>/.claude/skills/story-forge-*/
  writes references/ from settings              │ cwd = vault root
                                                │ reads canon, scenes, schema, house rules
                                                ▼
                                  <proposals folder>/  reports (.md) + proposals (.json)
  Workbench "Proposals" tab  ◀───────────────────┘
  review → accept → write via the undo-journaled write path
```

- **The plugin never calls an AI and makes no network request.** The AI runs in the user's own tool,
  started by the user. Privacy stays "vault content remains local".
- The AI's working directory is the **vault root**, so skills are project-level skills
  (`<vault>/.claude/skills/`). This works the same on the host (`cd <vault> && claude`), in a
  container that mounts the vault, and in Claude Desktop with a filesystem connector.

## Rules for every Story Forge skill

1. **Generic.** A skill must work in a fresh vault that has only Story Forge installed (the demo /
   test vault is the acceptance test). It names no series, no language, no folder layout, no writing
   process. Examples in skills use neutral sample data.
2. **Schema at runtime, not hard-coded.** Field names, relation fields, enums and categories are read
   from the vault's FileClasses / schema at run time. User-defined Codex categories therefore work,
   and schema changes reach the skills without a skill update. A skill may *describe* the core scene
   relations (`pov`, `characters`, `location`, `plotlines`, `storyDay`, `status`) as the starting
   point, but the vault's schema wins.
3. **No direct note edits.** Skills are read-only over the vault. They write only into the
   **proposals folder** (plugin setting): a report (`<skill>-<date>.md`) and, where the skill
   suggests changes, a proposal file (`<skill>-<date>.json`). Applying a proposal is the plugin's
   job (see "Proposals tab").
4. **House rules are an extension point.** Each skill reads an optional house-rules note (plugin
   setting, default `Story Forge AI house rules.md` in the plugin's meta folder; empty = none) before
   it starts. House rules may set: output language, severity order, which folders count as canon /
   manuscript / planning, extra checks, terms to use. On conflict the vault's `CLAUDE.md` and the
   house rules win over the skill's defaults. Skills never require the note to exist.
5. **Self-contained folders.** `SKILL.md` + `references/` (+ `scripts/` only if needed). No
   references into another skill's folder; shared material is duplicated per skill by the installer.

## Skills (first set)

### `story-forge-continuity-check`
- **Trigger:** "continuity check", "does this scene contradict the canon", "check chapter 4".
- **Input:** a scene note (or a chapter / range of scenes); the entity notes it links through its
  relation fields and wikilinks; earlier scenes by `storyDay` / order.
- **Checks:** behaviour vs. established traits and relations; physical facts (appearance, age,
  names, ownership) vs. entity frontmatter; timeline order vs. stated elapsed time in prose; object
  ownership/state; location consistency.
- **Output:** report, findings most severe first, each with the scene passage, the contradicting
  fact and its source note. Optional proposal entries for frontmatter facts that the prose
  establishes but the entity note lacks (never for prose changes).

### `story-forge-plot-holes`
- **Trigger:** "find plot holes", "unresolved threads", "what did I set up and never pay off".
- **Checks:** a plotline introduced but never resolved; an object or lore entity referenced and
  dropped; a character present in scenes without arc progression; scenes not assigned to any
  plotline.
- **Output:** prioritised report. No proposals.

### `story-forge-extract-entities`
- **Trigger:** "which characters/places in this chapter have no note yet", "extract entities".
- **Input:** scenes; existing entity notes (titles, aliases).
- **Output:** proposal with new entities (category, title, aliases, frontmatter facts found in the
  text with the quoting passage) and new facts for existing entities. The plugin creates notes via
  its template / FileClass path, so the result looks exactly like a note made in the Codex.

### `story-forge-canon-lint` — **open, decide in the spec**
Mechanical cross-note checks: wikilinked entities without a note, scenes missing required
frontmatter, `first_appearance` pointing at a missing scene, relations that are not reciprocated.
Most of this needs no judgement. Options:
- **A — skill**, like the others (cheap to ship, but uses an AI for deterministic work);
- **B — plugin code**, shown as warnings in the Codex / Workbench (fast, always current, but
  `docs/claude-skills.md` says the plugin deliberately computes no warnings);
- **C — split**: deterministic checks in the plugin as a command producing the same report format,
  the judgement part (e.g. "is this relation really one-sided?") in the skill.
Decide with the views roadmap; do not ship A and B with overlapping checks.

### Later: `story-forge-pacing`
Screen-time per character, scenes per plotline, act balance. Analytical only, no quality judgement.

## Installing the skills

- Skills are markdown files bundled into the plugin build.
- Command **"Story Forge: Install AI skills"** + a section in the settings tab, with a target picker:
  Claude Code → `.claude/skills/`; Codex / Antigravity → `.agents/skills/`; Gemini CLI →
  `.gemini/skills/`. Each skill in `story-forge-<name>/`.
- Preview before writing: per file *create / unchanged / update available*.
- **Never overwrite.** A newer bundled version is written next to the existing file as
  `SKILL.new.md` (and `<file>.new.md` in `references/`), with a notice. Version in frontmatter:
  `story-forge-skill-version`.
- **Namespace ownership.** The installer writes and updates only paths that start with
  `story-forge-`. Anything else in the skills folders belongs to the user or to other tooling and is
  never touched or listed as "unknown".
- At install time the installer writes `references/vault-model.md` per skill from the current
  settings: FileClasses folder, categories in scope, excluded folders, proposals folder, house-rules
  path. Re-running the install after a settings change offers updated references (same `.new.md`
  rule).
- Desktop only (`Platform.isDesktop`); hidden on mobile. The files sync to mobile like any other
  vault file and do no harm there.

## Setup prompt for Claude Desktop

For users without a terminal. A static text file shipped with the plugin; a **"Copy setup prompt"**
button in the settings tab copies it. Copying is the only plugin action. Draft:

```
You are setting up Story Forge AI skills for my Obsidian vault. Work as a step-by-step wizard:
ask one question at a time, wait for my answer, never skip ahead.

1. Vault access. Check whether you can read and write files in my vault (a filesystem connector or
   any other file tool). If not, tell me to connect one — e.g. the official filesystem MCP server
   pointed at the vault folder — and stop.

2. Skills. Look for folders named `story-forge-*` in `.claude/skills/` in the vault. If there are
   none, tell me to open Obsidian → Settings → Story Forge → AI skills → Install, and stop.
   Otherwise read each SKILL.md and its references/vault-model.md and list the skills you found.

3. House rules. If vault-model.md names a house-rules note and it exists, read it and summarise it
   in three lines.

4. Existing memory. If you already have memory entries about Story Forge, show them and ask
   whether to replace or keep them.

5. Rules to remember. Show me these rules, then ask for confirmation before saving them:
   - For story analysis requests (continuity, plot holes, missing entities), follow the matching
     Story Forge skill.
   - Never edit notes in the vault. Write reports and proposals only into the proposals folder
     named in vault-model.md.
   - Read the house-rules note and the vault's CLAUDE.md first; they win over skill defaults.

6. Save the rules and the list of skills to memory. Tell me what was saved.
```

## Proposals tab (plugin side)

- A Workbench tab (and command) listing proposal files in the proposals folder.
- Each entry shows target note, field, current value, proposed value, source passage, skill.
- Accept / reject per entry or for a file. Accepting writes through the existing frontmatter write
  path, **journaled** — so every accepted proposal can be undone with "Story Forge: Undo last
  change".
- New entities are created through the same template / FileClass path as the Codex "new" action.
- Proposal files are validated against a JSON Schema shipped with the plugin (also copied into each
  skill's `references/`). Invalid entries are listed with the reason, never applied.
- After a file is fully handled: move to trash or mark handled (setting).

Proposal format (draft):

```json
{
  "story_forge_proposal": 1,
  "skill": "story-forge-extract-entities",
  "created": "2026-11-11T14:30:00",
  "source": ["Manuscript/Book 1/Scene 12.md"],
  "entries": [
    { "op": "create", "category": "character", "title": "Anna Berg",
      "fields": { "role": "minor", "aliases": ["Anna"] },
      "evidence": [{ "note": "Manuscript/Book 1/Scene 12.md", "quote": "…" }] },
    { "op": "set", "note": "Codex/Characters/Lena.md", "field": "eye_color",
      "value": "green", "evidence": [{ "note": "Manuscript/Book 1/Scene 3.md", "quote": "…" }] }
  ]
}
```

`op` in v1: `create` (new entity) and `set` (frontmatter field, only if empty unless the user
confirms the replacement). No body edits, no deletes, no renames.

## Out of scope

- Story Forge calling an AI or any network API itself.
- Skills that write or rewrite prose, or that encode a writing process, a genre, or a language.
  That belongs to the vault owner's layer.
- Skills editing notes directly, including "small fixes".
- Bundling AI clients, API keys, or model settings.
