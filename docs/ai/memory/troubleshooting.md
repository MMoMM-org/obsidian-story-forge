# Troubleshooting Memory

<!-- 2026-08-01 -->
- `npm test` alone will NOT catch a store-type breaking change: vitest/esbuild transpiles without type-checking, so adding required fields to `ViewRecord` (or similar core types) can leave `npm test` green while `npm run typecheck` / `npm run typecheck:test` go red across every consumer that builds the type as an object literal. Always run `npm run typecheck` (and `typecheck:test`) after widening a shared type, not just `npm test`. Example: spec-008 T3.1 added required `kind`/`surfaces` to `ViewRecord` — broke tsc in `src/catalog/CatalogService.ts`, `src/import/ViewImporter.ts`, and ~13 test files, none of which were listed as owned by that task.

<!-- 2026-08-03 -->
- **A fix that lands can leave stale comments elsewhere describing the now-fixed limitation as still-open, or listing a collaborator that went away.** Spec-008 T4.3 review caught two in one pass, both in the same task's own diff: (1) `tableCard.ts`'s docstring said the grid-density limitation was "not this Card's" concern, unowned, right after the *same task* had already closed it (`d5f6cf2`'s `sf-cx-grid--<id>` fix); (2) `shared.ts`'s `fieldChip` docstring listed Hero as a caller after the S91 rebuild (`853bff1`) moved Hero off `fieldChip` entirely. Class of defect worth actively re-scanning for after every fix: search sibling files for comments that name *this exact limitation* or *this exact function* as still true, not just the file you just edited — is the one that's easiest to miss because the code compiles and every test still passes.
